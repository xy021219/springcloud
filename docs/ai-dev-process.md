# 本项目的 AI 开发过程

这份说明只写这个仓库实际在用的做法。人负责定范围和放行，AI 负责按已放行的范围改仓库。没点头的业务代码不写。

## 人始终在环里

AI 可以读代码、写规格、改实现、跑命令。下面几件事它不能自己做完：

- 新功能的规格写完之后，等人点头，再写业务代码。
- 表结构要变时，先给出语句，停下等确认。禁止用 `ddl-auto: update` 悄悄改表。
- 要从外部仓库借鉴实现时，先给出候选和许可证，点头之前不把别人的代码抄进来。
- 规格里没有的页面不加。不在若依之外再做一套登录或微服务。
- 没跑过的检查写成「未实测」，不写成已经通过。

这些话写在 `AGENTS.md` 里。每次对话都会读到，所以暂停点不会只存在于某一次聊天里。

## 技能是什么

长步骤不写进 `AGENTS.md`。`AGENTS.md` 只保留项目事实和必须停下的规则。具体怎么做，放在技能文件里。技能是一份带触发条件的说明书：描述里写明什么时候用，正文写步骤和禁止事项。

本仓库有两个技能，都在 `.cursor/skills/`：

| 技能 | 何时用 | 人要做什么 |
| --- | --- | --- |
| `spec-plan` | 新功能动手前，或人说先讨论方案、先不要写代码、出个规格 | 看完规格后点头。点头前没有业务代码 |
| `change-log` | 任务收尾，或人说写变更记录、留痕 | 看记录里的命令和结果是不是这次真跑过的。收尾时不借机改业务代码 |

本机还有一个技能 `reuse-search`，`AGENTS.md` 点名要先走它。仓库里没有同名副本，所以用本机这一份。它用在要新引入通用机制的时候，例如解析、导出、分页、重试、限流。只属于本业务的规则，例如「只能改 1 到 3 列」，不过这三道门，写明跳过原因即可。

技能也是人写的约束。做业务时不改技能来绕过暂停点。以后某条流程要固定下来，就加或改对应的 `SKILL.md`，而不是把长步骤堆进 `AGENTS.md`。

写一个技能时至少有这三块：

1. `name` 和 `description`：用什么话说的时候必须读它。
2. 步骤：先看仓库里已有的接口、页面和表，没有就写「还没有」。
3. 停止条件：哪一步必须等人，例如点头、确认 SQL、确认可以引用外部代码。

## 提出需求之后怎么走

先看改动有多大，再选路径。

**单文件小改。** `AGENTS.md` 允许直接改，改完跑相关检查，用一句话说明。`spec-plan` 更严：这种改动写在回复里，先问一句「直接改？」。两边不一致时，采用更严的那条，先问再改。

**新功能或需求变更。** 走 `spec-plan`。

1. 读现有代码。确认改动在 `backend/` 还是 `frontend/`，已有的接口、页面、表是什么。
2. 若要引入新的通用库或机制，先过 `reuse-search`。本仓库已有同类实现就沿用。这次读写 `.xlsx` 沿用已有的 Apache POI，图表沿用已有的 ECharts。列数规则是本业务的，跳过外部搜索。
3. 把规格写到 `docs/specs/YYYY-MM-DD-<短横线英文名>.md`。里面只有四段：目标、范围（含不做什么）、输入输出、验收。验收要写成能执行的检查，不写「运行正常」。
4. 停下，把规格交给人。人点头之前不改业务代码，不改菜单，不改已有规格正文。
5. 点头之后只改规格里列出的文件。涉及业务规则、接口契约或数据转换时，按 spec-plan 的检查先行：先跑出失败再改实现。样式、文案、布局不强制自动测试。
6. 按验收跑命令或打开页面。没走到的步骤保持「未实测」。
7. 收尾用 `change-log`，追加到 `docs/changes/当天日期.md`，不覆盖已有条目。记录里的数字来自这次命令输出。

改表列数是按这个顺序做的。业务要求从「恰好两列」改为「1 到 3 列」，并在导出表头标出改过的列。规格写在 `docs/specs/2026-10-28-sheet-column-range.md`。人回复「就这么做」之后，才给 `ruoyi-admin` 加上测试依赖，先看到测试因旧规则失败，再改实现。改完后 3 个用例通过。浏览器里的勾选和导出当时没走完，变更记录写的是未实测。

开发报表是另一次需求：页面按接口画周报，数字用模拟数据，不接外部模型。规格在 `docs/specs/2026-10-28-ai-report.md`。那次没有单独再停一次等第二句确认，需求本身就是在同一次任务里提出并实现的。需要严格停顿时，以列数变更为准。

## 暂停点

遇到下面任意一条，停下来，把事实和下一步交给人。不要先改完再解释。

| 暂停点 | 停下来时交出什么 | 人确认之后才能做 |
| --- | --- | --- |
| 新功能或行为变更 | `docs/specs/` 里的规格 | 写业务代码 |
| 表结构要变 | 完整 SQL。说明动哪些表、会不会删数据 | 执行语句 |
| 要引用外部实现 | 一到两个候选、它解决什么、用或不用的理由、许可证 | 把依赖或思路写进仓库 |
| 单文件小改但拿不准是不是小改 | 回复里的改法，并问「直接改？」 | 修改文件 |
| 验收做不到 | 做到哪一步、哪一步没跑、原因 | 决定算不算完成，或补做 |

另外两条是硬停止，不因为对话里说了「继续」就放开：

- `backend/sql/ry_20260417.sql` 和 `quartz.sql` 已经导入过。它们含有删除表的语句，不要再执行。
- 生产连接只用环境变量 `MYSQL_URL`、`MYSQL_USER`、`MYSQL_PASSWORD`。配置里不写 `ddl-auto: update`。

菜单写入已有的 `sys_menu` 不是改表结构，所以列数变更没有为它停下来建表。已经插入过的菜单不要再插一次。

## 做的时候要守住的门槛

这些不是每次都要等人回话，但人在看结果时要核对这些有没有被绕过。

- 范围以规格为准。规格写了不改登录、不建业务表，实现里就不要出现这些改动。
- 同一条规则在页面和接口各写一次。页面上的限制只是少一次无效请求，接口必须再拒绝。列数就是这样：页面禁止第 4 列，接口对 0 列和 4 列返回「请选择 1 到 3 列」。
- 先有失败的检查，再改实现。失败说明检查确实在卡旧行为。一上来就通过，看不出检查有没有写对。
- 变更记录只追加，不改写旧条目，也不在记记录时顺手改业务代码。反复会碰到的问题才补进 `AGENTS.md`。只发生一次的，写在当天记录里。
- Windows 上写出的中文文件可能是 GBK。Maven 按 UTF-8 编译时会报不可映射字符。提交或打包前要确认源码是 UTF-8。
- 全局过滤器会改写一部分请求正文。导出单元格里的原文若被改掉，要在规格里说明排除哪一个接口，而不是关掉整个过滤。
- 页面是否可用，以人在浏览器里走完为准。命令通过但页面没打开，记录里就分开写。

## 人具体看什么

点头前看规格：目标是不是一句话能做完，不做什么有没有写上，验收能不能照着执行。看不懂的句子退回去改规格，不进入写代码。

点头后看三样：改动的文件是不是规格里那几份；该失败的检查是否先失败过；记录里的命令、时间和「未实测」是否和实际一致。

不看 AI 对过程的口头说明。以规格、测试输出、变更记录和页面为准。
